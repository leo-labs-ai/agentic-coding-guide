1. The big idea

Writing code has become cheap. You pay for tokens and software gets built. The hard part is building software that is right for the business, that someone can maintain, and that can grow with the people using it.

80%

An agent can get you most of the way from a rough brief: a working proof of concept in a day, a first version of a feature, the boring plumbing.

20%

The last stretch is where the value is. Knowing the client, the market, and what "right" looks like. That still needs experienced people steering.

So the goal isn't "AI writes code for me". The goal is an environment where people can try ideas safely, and where anything that ships has been checked properly. Engineers end up spending their time on deciding and reviewing, not typing.

A useful way to think about it: the harness is everything around the model. What context it reads, which tools it can use, what counts as done, and how work moves between people and agents. Better harnesses beat clever prompts.

2. Four ways to direct an agent

LevelWhat you doWho holds the context
PromptOne message, one answerYou
ConversationYou steer it step by stepYou, reviewing every step
PlanYou agree a plan and the criteria it will be judged onThe plan is the contract
DelegationYou hand over a job and it runs on its ownYou review the outcome

The unit of work moves from a message to a job with acceptance criteria. Most people get stuck at "conversation". Getting to "plan" is the biggest jump, and it's mostly a habit change, not a tooling one.

3. The agent loop

Every good run follows the same loop:

  1. Orient. Read the task, the codebase and the relevant procedures before deciding anything.
  2. Plan. Write out an explicit plan and the criteria the result will be judged against.
  3. Execute. Do the work in an isolated sandbox, with only the tools the task needs.
  4. Judge. Tests, checks and a reviewing agent score the result against the criteria. If it fails, back to planning.
  5. Learn. Keep the outcome, the diff and the reviewer's edits so the next run is better.

The loop is bounded by three things: the tools it's allowed, the budget it has, and the permissions it holds.

4. Two human gates

RequestGate 1: what and whyAgent loopProof of workGate 2: approved to shipDeploy

Gate 1, before the work

  • The agent restates the task in its own words, so a misunderstanding shows up before any work starts.
  • Agree why it's being done and what it should change.
  • Agree the acceptance criteria.

Gate 2, after the work

  • The diff, plus a plain summary of what changed.
  • Each criterion marked pass or fail, with evidence attached.
  • Test output from the real pipeline, not the agent saying it passed.

If Gate 2 says no, the work goes back into the loop. People spend their attention on criteria and approvals rather than on keystrokes.

5. Practical habits

Context lives in the repo
Standards, procedures and architecture notes go in the repository (a README, an AGENTS.md or CLAUDE.md, a docs folder), not in your prompt. Agents read them every run, and they get reviewed like code.
Skills are written procedures
A release checklist, an incident runbook, a proposal format. Write them down once, version them, and point agents at them.
Least privilege
Give each task only the access it needs. For example: can write to the repo and deploy to staging, can't deploy to production, can't see customer data.
Ask, don't guess
When a decision is missing, the agent should stop and ask. Save the answer in the project so later runs already know it.
Proof of work
Before and after screenshots, test output, a clear diff. "It works" isn't evidence.
Small jobs, in parallel
Independent tickets can run as separate agents on separate branches at the same time.
A crew beats one long chat
One agent plans, implementers build, a reviewer checks each piece, and a verifier judges the whole against the criteria.

6. The bigger setup

Once a team is comfortable with the habits above, the next step is moving the work off individual laptops into a shared setup.

Software factory

A shared cloud environment that runs around the clock. You can start a session with a few agents, then pull in a designer or the product owner. They see the whole conversation and can add colours, icons or feedback without needing to know the technical side.

Agents in CI/CD

Every change goes through automated review: code quality, tests, and whether it actually runs on the server. Agents can handle deploys, health checks and rollbacks. A person approves the pull request that says "this goes to production". Test environments match production apart from real client data.

One gateway

Every model call goes through one place. You can see token spend, choose which models are used, control who can reach which agents and data, and spot problems such as a poor cache rate. Simple work goes to cheaper models, hard reasoning to the strongest ones.

Where this is heading: people will expect software they can talk to. Their own agent asks questions of a dashboard and changes it to suit them, instead of waiting weeks for a dev team. Building that way internally is good practice for building it for others.

7. Agentic systems overview

A picture of how the pieces fit together once you go beyond one person and one agent.

The basic flow

Intentrequests, tickets, goals Controlsplit the work, pick agents, set budgets and guardrails Executionagents in isolated workspaces with scoped tools Outputmerged code, deploys, finished tasks, plus an audit trail

The crew

A planner splits the work across implementers running in parallel. Each implementer has its own reviewer. A verifier judges the assembled result against the criteria, and anything that fails goes back to the implementer that made it. They all share the same project context.

Organise it like a team. People hold the accountable roles and own the gates. Lead agents own an area (building, operations, checks) and hand work to specialists, each with a clear remit, a budget and a list of systems it may touch. Adding capacity means adding specialists, not writing a longer prompt. Any run can be opened, commented on, paused or steered while it's going.

Tools, skills and grants

Capability is granted per task. A run gets the tools it needs, the skills that describe how to use them, and nothing else. Access comes as short-lived credentials matched to the task, and every call is logged.

Environments

Each team or organisation gets a private workspace, and each run gets a fresh, disposable sandbox inside it. Anything that needs to outlive the run (logs, results, files) is stored separately, so throwing a sandbox away loses nothing.

Real systems, under control

Agents can work in real business systems, but through reviewed changes rather than direct writes. Records, procedures and configuration live under version control, so every agent change is a diff with an author and a reviewer, and it can be undone. Anything sensitive, such as a payment or an official submission, stops and waits for a person to approve it on their own device. If nobody answers, the request expires and nothing happens.

Asking in the right place

When a run needs a decision, it writes the question and the options, and sends it wherever the person already is: email, chat, a message on their phone. Nobody has to open a dashboard. The answer is saved to the project so the question doesn't come up again.

The software lifecycle

  1. Intakethe ask
  2. Decidescope and criteria
  3. Buildbranch and diff
  4. Verifytests and evals
  5. Reviewhuman gate
  6. Deploypipeline
  7. Observehealth checks

Failed checks go back to "decide". After a deploy, health checks can roll a bad release back, open an issue and send it round again. Agents use the same repository, CI and deploy pipeline as everyone else. No parallel setup.

The same idea works for the business around the product: signal, research, draft, policy check, human approval, execute, measure. Nothing customer-facing sends itself.

Getting better over time

Every run leaves a record: the task and criteria, the diff, the check results, what a reviewer changed or rejected, and the cost and time. That record becomes test data. Past runs turn into graded cases, so a change to prompts, skills or model routing is measured before it ships, and failures become the next test. Human corrections at the gates are the strongest signal of all, because they define what good looks like.

8. Laptop, cloud or desktop app?

Desktop apps

The easiest way in for non-technical people. The Claude or ChatGPT desktop apps are good for drafting, research, analysis and small tools. Start here if you don't write code.

Coding agents

Claude Code, Codex, Cursor, pi and similar tools run in your terminal or editor against a real repo. Use plans, gates and tests. This is where most hands-on agentic coding happens.

Shared or cloud

Anything shared, long-running, or that touches production belongs in a shared environment, not on one person's laptop.

9. A first exercise

  1. Pick a small, real change in a repo that has a README and some tests.
  2. Ask the agent to restate the task and propose a plan with acceptance criteria. Check it. (Gate 1)
  3. Let it make the change on a branch.
  4. Have it run the tests and show you the output.
  5. Review the diff against the criteria and either merge it or send it back. (Gate 2)
  6. Write anything it got wrong into the repo docs, so the next run gets it right.

A quick demo for a group

Make a folder with a few hundred small text files and hide one real task in it (a list of sums to check, say). Ask an agent to find it and work through it, first on its own, then with sub-agents splitting the files. It shows how agents divide work up, and how much faster parallel work is.

10. Things to watch out for

  • Context bloat. Too much in the prompt makes results worse. Keep instructions short and keep them in the repo.
  • Tool loops and scope creep. Agents quietly doing more than you asked. Gate 1 and an explicit "out of scope" list help.
  • Trusting claims over checks. A model's answer is only a claim until a real check passes.
  • Secrets in prompts or diffs. Never paste keys or passwords. Use proper secret storage and environment config.
  • Skipping the boring part. Tests, a README and a working build are what make agents useful. Without them, you're back to reviewing every line by hand.

11. A few terms

Agent
A model that can use tools (read files, run commands, open pull requests) in a loop until a task is done.
Harness
Everything around the model: context, tools, permissions, checks and handoffs.
Acceptance criteria
The specific things that must be true for the work to count as done.
Sandbox
An isolated, disposable environment where an agent can work without touching anything else.
Gateway
A single point that every model call passes through, for metering, routing and access control.
Software factory
A shared, always-on environment where people and agents build, test and ship together.
