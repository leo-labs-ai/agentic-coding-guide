Harness engineering, in plain language

Agentic coding: a practical guide

How to work with coding agents so the output can be reviewed and is right for the people who use it. Twelve short sections, habits you can start today, and a set of longer articles for when you want the detail.

01The big idea

Writing code has become cheap. Building software that is right for the business, that someone can maintain, and that can grow with the people using it is still hard. That is where the effort goes now.

An agent is a model plus a harness. The model is rented: everyone gets the same one, and it changes every few months. The harness is everything around it that you control: the instructions it reads, the tools it can call, the context it sees, the checks that judge its work, and the permissions that limit it.

Most of the gap between what a model can do and what you actually see is a harness gap. The agent did not know the rule, could not run the test, or was never told what done looks like. Fix those and the same model looks much smarter.

An agent can get you most of the way from a rough brief: a working proof of concept in a day, a first pass at a feature, the boring plumbing. The last stretch is where the value is. Knowing the users, the market and what right looks like still needs experienced people steering. So aim for an environment where people can try ideas safely, and where anything that ships has been checked properly. Having AI type the code for you is the easy part.

02Four ways to direct an agent

LevelWhat you doWho holds the context
PromptOne message, one answerYou
ConversationYou steer it step by stepYou, reviewing every step
PlanYou agree a plan and the criteria it will be judged onThe plan is the contract
DelegationYou hand over a job and it runs on its ownThe harness, and you review the outcome

The unit of work moves from a message to a job with acceptance criteria. Most people get stuck at conversation. Getting to plan is the biggest jump, and it is a habit change more than a tooling one.

Choosing a model is part of directing. Use the cheapest model that clears the bar for the job, keep the strongest for architecture, security and high-stakes review, and never let the builder grade its own work.

03The agent loop

A model on its own only produces text. It becomes an agent when a harness runs it in a loop: the model asks for a tool, the harness runs it, the result goes back in, and the model decides what to do next. Good runs follow the same shape.

  1. Orient. Read the task, the code and the relevant procedures before deciding anything.
  2. Plan. Write an explicit plan and the criteria the result will be judged against.
  3. Execute. Do the work on a branch or in a sandbox, with only the tools the task needs.
  4. Judge. Tests, checks and a separate reviewer score the result against the criteria. If it fails, go back to the plan.
  5. Learn. Keep the outcome, the diff and the reviewer's edits, and fix the harness where it let the agent down.

The judge step only works if the criteria are checkable. "Fix the double charge" is a wish. "One intended purchase creates one order, even when the request is sent twice" is something a test can prove.

04Two human gates

People spend their attention at two points: before the work starts and before it ships. Everything in between belongs to the loop.

  1. Requesta ticket or an idea
  2. Gate 1what, why and done
  3. Agent loopbuild and check
  4. Proof of workdiff and evidence
  5. Gate 2approved to ship
  6. Deploythe real pipeline

Gate 1, before the work

  • The agent restates the task in its own words, so a misunderstanding shows up before any work starts.
  • Agree why it is being done and what it should change.
  • Agree the acceptance criteria, and what is out of scope.

Gate 2, after the work

  • The diff, plus a plain summary of what changed.
  • Each criterion marked pass or fail, with evidence attached.
  • Test output from the real pipeline, not the agent saying it passed.

If you find yourself typing "continue" every few minutes, the harness has failed. The task was missing a criterion, a permission or a check, so the agent kept coming back to you instead. Fix that, and the next run needs you only at the gates.

05Context is scarce

Code is cheap now. The context window is not. Everything the agent sees in a session (instructions, files, tool output, its own earlier turns) competes for the same limited attention, and quality drops well before the window is full. Keep each task small enough to stay in what Matt Pocock calls the "smart zone".

  • One task, one session. Start fresh for new work. Clear rather than compact: a summary of a long session carries its confusion forward.
  • Knowledge lives in files. Decisions, rules and procedures go in the repo, not in a chat the next session will never see.
  • Keep AGENTS.md short. It is read on every turn, so each line must change what the agent does. Make it a map that points to deeper docs, not a manual.
  • Load detail on demand. Skills and reference docs are listed by a one-line description and read only when the task needs them.
  • Keep noise out. Save long logs and big API responses to a file, then read the slice you need.

Most tools also cache the start of each request, so standing instructions are cheaper to re-send than new material. That helps, but cached tokens still fill the window and are still paid for on every turn. Keep the stable part stable and the whole thing lean.

06Practical habits

Context lives in the repo
Standards, procedures and architecture notes go in the repository, where agents can read them and people can review them like code. What the agent cannot see does not exist for it.
Skills are written procedures
A release checklist, an incident runbook, a report format. Write it once, version it, and give it a description that says when to use it and when not to.
Guides and sensors
Guides steer the agent before it acts: instructions, skills, examples. Sensors check after: tests, linters, type checks, a reviewer. You need both, and good error messages say how to fix the problem.
Least privilege
Give each task only the access it needs. Write to the repo and deploy to staging, yes. Deploy to production or read customer data, no.
Ask, don't guess
When a decision is missing, the agent stops and asks. The answer is saved in the project so later runs already know it.
Proof of work
Before and after screenshots, test output and a clear diff. "It works" is a claim, not evidence.
Fix the harness, not the output
When the agent makes the same mistake twice, the fix belongs in the instructions, a check or a skill. Correcting the output by hand teaches it nothing.
A crew beats one long chat
One agent plans, implementers build, a reviewer in a fresh session checks each piece, and a verifier judges the whole against the criteria.

07Laptop, cloud or desktop app?

Desktop apps
The easiest way in for people who do not write code. Chat apps such as Claude or ChatGPT are good for drafting, research, analysis and small tools. A project with instructions and files is a small harness in its own right.
Coding agents
Claude Code, Codex, Cursor, pi and similar tools run in your terminal or editor against a real repo. This is where most hands-on agentic coding happens. Use plans, gates and tests.
Shared or cloud
Anything shared, long-running or touching production belongs in a shared environment, not on one person's laptop.

For browser and desktop work, use the lightest tool that does the job: an API before a browser, a browser before full computer control. Look, act once, look again.

08The software factory

Once a team is comfortable with the habits above, the next step is moving work off individual laptops into a shared setup that runs around the clock. People and agents work in the same place. A designer or product owner can join a session, see the whole conversation, and add feedback without knowing the technical side.

  1. Intakethe ask
  2. Decidescope and criteria
  3. Buildbranch and diff
  4. Verifytests and evals
  5. Reviewhuman gate
  6. Deploythe pipeline
  7. Observehealth checks
  • Agents in CI/CD. Every change gets automated review and tests. Agents can run deploys, health checks and rollbacks. A person approves the change that goes to production.
  • One gateway. Every model call goes through one place, so you can see spend, route simple work to cheaper models and control who reaches what.
  • A crew with remits. Each role has a clear job, a budget and a list of systems it may touch. Adding capacity means adding a specialist, not writing a longer prompt.
  • Disposable sandboxes. Each run gets a fresh workspace. Anything that must outlive it (logs, results, files) is stored separately.
  • Every run is data. The task, the diff, the checks and what a reviewer changed become test cases for the next change to prompts, skills or routing.

09Routines and loops

Agents do not have to wait for you. A routine runs on a schedule or when something changes: a nightly dependency check, a weekly report, a sweep for stale docs. A loop runs until a stop condition is met, such as "stop when the test suite passes".

  • Every routine needs logs, a way to run it now, a kill switch and a health check.
  • Use a cheap check to wake an expensive model only when something has changed.
  • The worker never grades its own work, and every step cites evidence.
  • After two failed fix attempts, stop and re-scope rather than letting it grind on.
  • A met stop condition is not the same as accepted work. A human still says yes to sending, deleting, paying or publishing.

10Exercises

Your first gated change

  1. Pick a small, real change in a repo that has a README and some tests.
  2. Ask the agent to restate the task and propose a plan with acceptance criteria. Check it. That is Gate 1.
  3. Let it make the change on a branch.
  4. Have it run the tests and show you the output.
  5. Review the diff against the criteria and merge it or send it back. That is Gate 2.
  6. Write anything it got wrong into the repo docs, so the next run gets it right.

Three short ones

  • Write a 20-line AGENTS.md. For every line, ask whether the agent would act differently without it. Delete the lines where the answer is no.
  • Audit a skill description. Write five prompts that should load it and three that should not. Check what actually happens.
  • Make a model table. List the jobs you give agents, and next to each the cheapest model that does it well enough.

A quick demo for a group

Make a folder with a few hundred small text files and hide one real task in it, such as a list of sums to check. Ask an agent to find it and work through it, first on its own, then with sub-agents splitting the files. It shows how agents divide up work, and how much faster parallel work is.

11Things to watch out for

  • Context bloat. More instructions do not mean better results. Past a point, they make results worse.
  • Scope creep. Agents quietly doing more than you asked. Gate 1 and an explicit out-of-scope list help.
  • Trusting claims over checks. A model's answer is only a claim until a real check passes.
  • Self-grading. The agent that wrote the code is the worst one to review it. Use a fresh session, and ideally a different model.
  • Plans nobody reads. A plan you skim and approve is noise. Read it, or make it shorter.
  • Auto-everything. A pipeline with no human taste in it produces slop. Front-end work especially needs human eyes.
  • Secrets in prompts or diffs. Never paste keys or passwords. Use proper secret storage and environment config.
  • Skipping the boring part. Tests, a README and a working build are what make agents useful. Without them you are back to reviewing every line by hand.

12Terms and further reading

Agent
A model that can use tools (read files, run commands, open pull requests) in a loop until a task is done.
Harness
Everything around the model: instructions, context, tools, permissions, checks and handoffs.
Acceptance criteria
The specific, checkable things that must be true for the work to count as done.
Skill
Written instructions for a type of task, loaded only when its description matches the job.
Tool
Something the agent can call to act on the world: run a command, query an API, open a page.
Context window
Everything the model can see on a given turn. Limited, and quality drops as it fills.
Prompt cache
Reuse of work for a request that starts with the same text as an earlier one. Cheaper, not free.
Sandbox
An isolated, disposable environment where an agent can work without touching anything else.
Gateway
A single point that every model call passes through, for metering, routing and access control.
Software factory
A shared, always-on environment where people and agents build, test and ship together.
