Context is scarce

Code is cheap now. The agent's attention is not. Most of harness engineering is deciding what goes into the window, when, and what stays out.

About 5 minutes to read

Everything an agent knows on a given turn is in its context window: the system prompt, your instructions, the skills it can see, every file it has read, every tool result, and the whole conversation so far. Context windows have grown large. That makes it tempting to put everything in. It does not work.

Bigger windows are not smarter windows

A model can retrieve a fact from a very long context. Reasoning well across all of it is another matter. Quality drops as the window fills: instructions in the middle get missed, older details blur, and the model starts confusing what it read with what it did.

Matt Pocock calls the early part of the window the "smart zone". Keep each task inside it and the agent stays sharp. A huge window gives you a huge amount of retrieval, not a huge amount of good thinking. In practice that means keeping tasks small, and watching how full the window is as you go.

New task, new session

The simplest habit is also the most effective. When the task changes, start a fresh session. Give each task its own folder or git worktree, so parallel jobs do not trip over each other.

When a session gets long, most tools offer to compact it: summarise what happened and carry on. It is better to clear. A summary keeps the conclusions and loses the reasons, and it carries forward whatever confusion built up. Write down what matters (the plan, the decisions, what is left) in a file, start a clean session, and point it at the file.

This is also why reviewers should run in a fresh session. An agent reviewing its own work, in the same window it built it in, is reading through all its own assumptions. A fresh reviewer sees only the diff and the criteria, which is what a reviewer should see.

Knowledge lives in files, not chat

Anything you explain in a chat is gone when the session ends. If it matters beyond today, put it where the next session will find it: the repo's instructions, a doc, a skill. Chat apps have the same idea in a different form. A project with standing instructions and a few reference files is a small harness, and it beats re-explaining yourself every time.

What goes in AGENTS.md

AGENTS.md (or CLAUDE.md) is read at the start of every session and stays in the window for every turn. Every line costs attention all the time. So the test for each line is simple: would the agent act differently without it? If not, cut it.

Rules it would otherwise break

  • Hazards: "Never edit db/migrations/ by hand; run pnpm db:generate."
  • How to verify: "Verify with pnpm test:unit."
  • Current direction: "Moving auth from sessions to JWT; new code uses lib/auth/jwt.ts only."
  • Where to look: "UI work: read docs/design-system.md."
  • Boundaries: "Changes in src/billing/ need human review."

Things it can work out or does not need

  • What the code already shows: the stack, the folder layout.
  • A copy of the README.
  • Generic advice: "write clean code", "be careful".
  • Live status, dates and counters, which go stale and change the prompt every session.
  • Shouting in capitals. It does not help.

Vague lines are worth rewriting rather than deleting. "Be careful with git" changes nothing. "Check git status before editing; never reset work you did not make" changes behaviour.

Aim for something like twenty lines. A file that grows forever is a sign it is being used as a diary. Write a pruning rule into the file itself, such as "prefer rewriting or pruning existing entries over appending", so the agent helps keep it short.

Progressive disclosure

The alternative to one big file is layers. Think of three tiers, by when you pay for them:

  • Always loaded. Identity, the few rules that must never break, and a routing table that says where to find everything else. Paid on every turn, so keep it small.
  • Flagged sections. Short blocks marked as applying only in some cases, such as "only if touching payments". Still paid for, but they steer attention.
  • Read when needed. Reference docs, skills and nested AGENTS.md files in subfolders. Paid only when the task needs them.

Loading everything up front fails in three ways. Rules in the middle get lost. Models can only juggle so many instructions at once before they start dropping some. And when a long session is compacted, rules that were loaded at the start can vanish from the summary. Give the agent an index, not the bodies.

Skills and tools

A tool performs an action: run a command, fetch a page, query a database. A skill supplies instructions for a type of task: how to cut a release, how to write the weekly report, how to debug a flaky test.

Skills are progressive disclosure in practice. The agent sees only each skill's short description. When a task matches, it loads the full text. So the description does all the selecting and the body does all the work. A good description says what the skill does, when to use it, using the words people actually type, and where a neighbouring skill takes over instead.

Descriptions are not free either. Every one is listed in every session. Install fifty skills and the list itself crowds the window, and some tools quietly drop descriptions that do not fit. A skill the agent never sees does not exist. A handful of sharp skills beats a drawer full of vague ones.

To check a skill, write five prompts that should load it and three that should not, then see what actually happens.

Keep noise out of the window

Tool output is the silent context killer. A full test log, a long API response or a page of HTML can fill a big share of the window in one call. Capture it once to a file, then read the slice you need with a search or a filter. The agent gets the three failing tests, not three thousand passing ones.

Code can do the same job earlier. If the agent needs overdue projects from a large export, a few lines of code that filter the data before the model sees it beat pasting the whole export in.

Checking context before you add it

Before you put something in front of an agent, a few quick questions help:

  • Where did it come from, and is it the authority on this?
  • Is it relevant to this task, and is it enough to act on?
  • Is it current?
  • Should this agent be allowed to see it at all?

Then put it at the latest point it is reliably needed. Grounding facts go in early. Detail for a specific step goes in at that step. Review criteria go in at review.

One more thing: pick the model first

Choose the model at the start of a session. Switching halfway through means the whole conversation is sent again to a model that has seen none of it, which is slow and expensive. The next article explains why.
