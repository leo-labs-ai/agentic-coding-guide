Harness engineering: the part you control

An agent is a model plus a harness. You rent the model. You build the harness, and that is where most results are won or lost.

About 5 minutes to read

Every team using coding agents gets access to the same few models. They change every few months, and each new one is a little better than the last. If the model were the whole story, everyone would get the same results. They do not. Two people can point the same model at the same repo and get a clean, tested change in one case and a confident mess in the other.

The difference is the harness: everything around the model that decides what it sees, what it can do and how its work is judged.

What a model actually does

A language model does one thing. It takes the text it has been given and produces more text, one token at a time, based on its training and on the context for this call. That is all. It does not remember yesterday. It does not know your codebase unless something put your codebase in front of it.

A tool call is also just output. When an agent "runs the tests", the model writes a request that says, in effect, "please run this command". The harness reads that request, runs the command, and puts the result back into the context for the next turn. The model never touched your machine. The harness did, on its behalf.

Once you see it that way, a lot of agent behaviour stops being mysterious. If the agent did not follow your naming convention, was the convention anywhere it could see? If it claimed the tests pass, did it have a way to run them? If it edited a file it should have left alone, did anything stop it?

The parts of a harness

Different tools package these differently, but the parts are the same everywhere.

  • Instructions. The standing rules the agent reads at the start of every session, usually an AGENTS.md or CLAUDE.md file in the repo.
  • Skills. Written procedures for a type of task, such as how to cut a release or how to debug a flaky test. The agent sees a one-line description of each and loads the full text only when it needs it.
  • Tools. What the agent can actually do: run shell commands, read and write files, drive a browser, call an API.
  • Context. Everything in the window on a given turn: the instructions, the files it has read, tool output, and the conversation so far.
  • Checks. The tests, linters, type checkers and reviewers that tell the agent, and you, whether the work is right.
  • Permissions. What it is allowed to touch, and which actions need a person to say yes.

Model choice belongs on the list too. Which model runs which job, and with how much thinking effort, is a harness decision rather than a fixed fact.

Guides and sensors

Birgitta Böckeler, writing on martinfowler.com, splits the harness into two kinds of control. Guides steer the agent before it acts: instructions, skills, examples, a well-trodden path through the code. Sensors give it feedback after it acts: tests, linters, type checks, a second model reviewing the diff.

Some sensors are deterministic. A type checker gives the same answer every time, quickly and cheaply. Others are judgement calls made by another model. Both are useful, and they fail in different ways, so a good harness has some of each.

A useful rule for sensors: success is silent, failure is verbose. A passing check should cost the agent almost nothing to read. A failing one should say exactly what is wrong and how to fix it. "Lint failed" sends the agent hunting. "Imports from lib/legacy are not allowed in new code; use lib/auth/jwt.ts" fixes the problem in one step.

What the agent cannot see does not exist

Ryan Lopopolo's write-up of building a product with Codex makes this point well. Knowledge that lives in a chat thread, a slide deck or someone's head is invisible to the agent. If a decision matters, it has to be in the repo, in a form the agent can find.

That does not mean one giant instructions file. His team's AGENTS.md is a short map: what this project is, the rules that are easy to break, and where to look for more. The detail lives in docs the agent reads when the task calls for it. A long manual loaded on every turn crowds out the work and gets ignored in the middle.

Two more ideas from the same piece are worth keeping. Enforce invariants rather than implementations: "every endpoint has an auth check" is a rule a test can hold, while "write the handler like this" goes stale. And clean up on a schedule. Agents copy what they see, so old patterns spread unless something sweeps them out.

Where a fix belongs

When an agent gets something wrong, the instinct is to correct it in the chat and move on. That fixes the output once. The next session makes the same mistake.

A better habit is to ask which layer should have prevented it, from lightest to heaviest:

  1. The task itself. Was something missing from this one request? Add it to the brief.
  2. Standing instructions. Is it a rule that applies every time? One line in AGENTS.md.
  3. A check. Does the rule keep getting broken anyway? Turn it into a test, a lint rule or a hook that blocks the bad action.
  4. A skill. Is it a whole procedure with several steps and judgement calls? Write it down as a skill with its own checks.

One rule of thumb saves a lot of time: rewording cannot fix a missing capability. If the agent cannot run the browser, no amount of "please check it in the browser" will help. Give it the tool, or change the criterion to something it can check.

A small example

Sam maintains the web shop for Fernhill Supply, a small garden-tools retailer. Every time Sam asks an agent to add a database column, the agent hand-edits an old migration file instead of generating a new one. Sam fixes it, explains, and the next session does it again.

Sam adds one line to AGENTS.md: "Never edit db/migrations/ by hand; run pnpm db:generate." That mostly works. A month later it happens again during a long session, so Sam adds a check in CI that fails if an existing migration file changes, with an error that names the command to run instead. Now the rule holds whether or not the agent remembers it.

Nothing about the model changed. The harness did.

Why this is worth the effort

Models will keep improving, and each upgrade will lift everyone a little. A good harness compounds. Every rule written down, every check added and every procedure turned into a skill makes the next run better, whatever model is underneath. When a better model arrives, it lands in a harness that already knows your project.

So when an agent does something dumb, resist blaming the model first. Ask what the harness gave it.
