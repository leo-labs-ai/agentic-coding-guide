From laptop to software factory

Where agent work should run depends on who is doing it, how long it takes and what it touches. Past a certain point, the answer is a shared place that never switches off.

About 5 minutes to read

Three places to run an agent

The desktop app

For people who do not write code, the chat apps from the big model providers are the easiest way in. They are good for drafting, research, analysis and small tools. Most have a projects feature: standing instructions plus a set of files that every chat in the project can see. That is a harness in miniature, and using it well (short instructions, the right reference files, one project per kind of work) gets much better results than starting from a blank chat each time.

A coding agent on your machine

Tools such as Claude Code, Codex, Cursor and pi run in a terminal or editor against a real repo. They can read the code, run tests and make changes on a branch. This is where most hands-on agentic coding happens, and where the habits in this guide pay off most: plans, criteria, gates and tests.

A laptop is a fine place to start. It stops being fine when the work is shared, runs for a long time, or touches anything in production. A job that dies when you close the lid, or that only one person can see, is a bottleneck.

A shared environment

Anything shared, long-running or production-facing belongs somewhere shared. That might be a cloud workspace, a CI system that can run agents, or a dedicated server. The point is that the work, its history and its results are visible to the team, and nothing depends on one person's machine being on.

Browsers, desktops and the lightest tool

A lot of real work happens in web apps and desktop software with no clean API. Agents can drive a browser, and some can control a whole desktop through screenshots. Use the lightest tool that does the job:

  1. An API, if there is one. Fast, reliable and easy to check.
  2. A browser the agent controls, if there is not.
  3. Full computer control as a last resort. It is slow, and screenshots fill the context window quickly. Save them to disk and keep only the current one in view.

Whichever you use, the pattern is the same: look, act once, look again. An agent that fires off five clicks without checking the page in between is guessing.

A browser side panel that fills in a form is a good small case. The agent works only in tabs it opened itself. It pauses for a person whenever there is a login or a two-factor prompt. And a person reviews the filled form before anything is submitted.

When you need to show an agent something on screen, point rather than describe. Most tools now let you select or annotate an element. "This button" with a highlight beats a paragraph about where the button is.

The software factory

When a team gets comfortable with agents, the natural next step is a software factory: a shared environment that runs around the clock, where agents and people build, test and ship together.

It changes who can take part. A session can start with a developer and a few agents, then pull in a designer or a product owner. They see the whole conversation and can add colours, copy or feedback without needing to know the technical side.

The lifecycle

  1. Intakethe ask
  2. Decidescope and criteria
  3. Buildbranch and diff
  4. Verifytests and evals
  5. Reviewhuman gate
  6. Deploythe pipeline
  7. Observehealth checks

Failed checks go back to Decide. After a deploy, health checks can roll back a bad release, open an issue and send it round again. Agents use the same repo, CI and deploy pipeline as everyone else. There is no separate, special path for agent work.

The pieces

  • Agents in CI/CD. Every change gets automated review for quality and tests, plus a check that it actually runs. Agents can handle deploys, health checks and rollbacks. Test environments match production, without real customer data. A person approves the change that goes to production.
  • One gateway. Every model call goes through one place. That gives you spend by team and job, routing of simple work to cheaper models, control over who can reach which agents and data, and early warning of problems such as a falling cache hit rate.
  • A crew, not one long chat. A planner splits the work. Implementers build in parallel, each with its own reviewer. A verifier judges the assembled result against the criteria and sends failures back to whoever built them.
  • Roles with remits. Each agent role has a clear job, a budget and a list of systems it may touch. Adding capacity means adding a specialist, not making one prompt longer.
  • Workspaces and sandboxes. Each team gets a private workspace. Each run gets a fresh, disposable sandbox inside it. Logs, results and files that must outlive the run are stored separately, so throwing a sandbox away loses nothing.
  • Least privilege. Access is granted per task, with short-lived credentials. A typical build run might be allowed to write to the repo and deploy to staging, and denied production deploys and customer data. Every call is logged.

Real systems, under control

Agents can work on real business systems too: records, procedures, configuration. The safe way is through reviewed changes rather than direct writes. Keep those things under version control and every agent change becomes a diff with an author and a reviewer, which can be undone. Anything sensitive, such as a payment or an official submission, waits for a person to approve it on their own device, and expires if nobody does.

Getting better over time

Every run leaves a record: the task and criteria, the diff, the check results, what a reviewer changed or rejected, and the time and cost. That record becomes test data. Past runs turn into graded cases, so a change to prompts, skills or model routing is measured before it ships, and each new failure becomes the next test case. Human corrections at the gates are the strongest signal of all, because they show what good looks like.

Start smaller than you think

A factory sounds like a big build. It does not have to start that way. A few sharp skills beat dozens of vague ones. A reviewer agent is a better first addition than more implementers, because it raises the quality of everything that follows. Write a process down and run it by hand before you automate it.

And keep the split in mind. Agents get you most of the way quickly: a proof of concept in a day, the plumbing, the first draft. The last stretch, where the work has to fit the users and the business, still needs people who know both. A good factory gives them more time for that part.

Where this is heading

People will increasingly expect software they can talk to. Instead of waiting weeks for a change, they will ask their own agent to adjust a dashboard or a report to suit them. Building software this way internally is good practice for building it for others.
