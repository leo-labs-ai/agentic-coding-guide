Human gates, and why every "continue" is a harness failure

People should spend their attention where judgement counts: agreeing the job before it starts, and approving it before it ships. Not nudging an agent along in between.

About 5 minutes to read

Watch someone new to coding agents and you will often see the same pattern. They give the agent a task. It does a bit, then stops and asks a question. They answer. It does a bit more and asks for permission to run a command. They approve. It reports progress and waits. They type "continue". An hour later they have a result and a sore wrist, and they could have written it themselves.

The agent was not being stupid. It was missing things it needed to keep going on its own: a decision, a permission, a definition of done. Each "continue" marks a spot where the harness had a gap and a person filled it by hand.

Two gates

A better arrangement puts people at two points, and lets the loop run in between.

  1. Requesta ticket or an idea
  2. Gate 1what, why and done
  3. Agent loopbuild and check
  4. Gate 2approved to ship
  5. Deploythe real pipeline

Gate 1: before the work

The agent restates the task in its own words. This is the cheapest bug fix there is. If it has misunderstood, you find out now, before it has built the wrong thing.

Then you agree three things: why the work is being done, what it should change, and the acceptance criteria that will decide whether it is finished. Add an out-of-scope list if the task sits next to something tempting. "Do not touch the refund flow" saves a long review later.

A plan only helps if you read it. A plan you skim and approve is noise that makes everyone feel safer. If the plans are too long to read properly, ask for shorter ones.

Gate 2: after the work

The agent hands back proof, not a story:

  • The diff, and a plain summary of what changed.
  • Each acceptance criterion marked pass or fail, with evidence attached.
  • Test output from the real pipeline, not the agent's word that tests pass.
  • Screenshots for anything visual: before and after.

Review the code, not just the summary. The code is the ground truth. A summary can be accurate and still leave out the part that matters.

If Gate 2 says no, the work goes back into the loop with a reason. The reason is valuable. It often points to the next thing to fix in the harness.

Reading a "continue" as a bug report

Every time you have to step in mid-run, ask what would have let the agent carry on without you. The answer is usually one of a few things.

  • A missing criterion. The agent stopped because it could not tell whether it was done. Write the criterion down and give it a way to check.
  • A missing decision. It needed to choose between two approaches and had no basis for choosing. Record the decision in the repo so it is there next time.
  • A missing permission. It kept asking to run the same safe command. Allow that command for this kind of task.
  • A missing tool. It could not see the result of its own work, such as a page in a browser, so it asked you to look. Give it the tool.
  • A task that is too big. It lost the thread halfway through. Split the work into smaller, vertical slices that each end in something testable.

Some interruptions are healthy. An agent that stops to ask before deleting data is doing its job. Aim for every question to be one only a person could answer, rather than for no questions at all.

When a decision is missing

Sometimes the agent does need a person, and the person is not at their desk. A good harness writes the question and the options down and sends it wherever that person already is: email, a team chat, a message on their phone. Nobody should have to open a special dashboard to find out they are blocking something.

When the answer comes back, it is saved to the project. The next run that hits the same question finds the answer instead of asking again.

Actions that always need a yes

Some actions should never happen without a person approving them, however good the agent is: sending a message to a customer, deleting data, paying for something, publishing anything public.

For these, approval should happen on the approver's own device, not in a text box the agent could type into. And the safe default is expiry. If nobody answers within a set time, the request lapses and nothing happens. An unanswered approval should never turn into a yes.

QA is the taste filter

It is possible to automate every step: an agent writes the code, another reviews it, a third tests it, and it ships. For some internal plumbing that is fine. For anything people will use, a fully automatic pipeline turns into a slop machine. Everything passes, and nothing is quite right.

Human review at Gate 2 is where taste lives. Does this feel right to use? Is this the copy we would write? Front-end work especially needs human eyes. Automated checks can tell you the button exists. They cannot tell you it is in the wrong place.

An example

Sam at Fernhill Supply asks an agent to add a "notify me when back in stock" button to product pages.

At Gate 1, the agent restates it, and Sam spots a gap: should the notification be an email or a text? Sam decides email only, notes it in the project docs, and agrees the criteria. The button appears only on out-of-stock items. Signing up twice does not send two emails. Nothing is sent until stock actually arrives. The checkout is out of scope.

The agent works through the loop without stopping. At Gate 2, Sam gets the diff, screenshots of the button on a phone and a laptop, and test results for each criterion. Sam notices the button text is clumsy, fixes it, and approves.

That correction goes into the project's copy guidelines. Next time, the agent gets it right first time. Two moments of human attention, both spent on judgement.
