Directing agents: from prompts to delegation

There are four ways to work with an agent. Most people stop at the second. The jump to the third is mostly a habit, and it changes what you can hand over.

About 4 minutes to read

The four levels

LevelWhat you doUnit of work
PromptAsk once, take the answerA message
ConversationSteer it step by stepA chat
PlanAgree a plan and criteria, then let it runA task with a definition of done
DelegationHand over a job and review the outcomeA job with acceptance criteria

Prompt

One message, one answer. Good for lookups, quick drafts and small, self-contained snippets. You hold all the context and you check the result yourself.

Conversation

You ask, it does a bit, you correct it, it does a bit more. This is where most people settle, because it feels productive and it is how chat apps are designed. The trouble is that you are the harness. You remember the rules, you notice the mistakes, you decide when it is done. The agent can only work as fast as you can watch it.

Plan

Before any work, the agent proposes a plan and the criteria the result will be judged on. You read it, fix it and agree it. Then it runs. The plan becomes the contract: the agent knows what done means, and you know what you will be checking.

This is the biggest jump. It needs no new tools. It needs you to spend five minutes up front instead of fifty minutes steering.

Delegation

You hand over a job, and the agent works through it on its own, often with sub-agents, and comes back with proof. You review the outcome at a gate. This only works when the harness carries what you used to carry in your head: the rules in the repo, the checks in the pipeline, the procedures in skills.

You do not have to delegate everything. The point is to know which level a task needs, and to make sure the harness can support it.

Moving up a level

Some signs you are ready to move from conversation to plan:

  • You keep correcting the same kind of mistake. Write the rule down.
  • You keep asking "is it done?" Write the criteria first.
  • You lose track of what the agent has changed. Ask for a plan and a summary.

And from plan to delegation:

  • The agent's plans rarely need fixing.
  • The checks are good enough that a passing run is usually right.
  • You find yourself approving the plan without changes, then typing "continue".

Picking a model

Choosing the model is part of directing the work. The rule is simple: use the cheapest model that clears the bar for this job. It helps to think in tiers rather than product names, because names change every few months.

Light
Lookups, scouting a codebase, sorting and summarising. Fast and cheap. Good for sub-agents that read a lot and report a little.
Bulk
Routine, well-specified changes at volume: renames, small fixes, test scaffolding.
Workhorse
Most real building and drafting. The default for feature work.
Flagship
Architecture, security, tricky debugging and high-stakes review. Slower and dearer, and worth it where a mistake is costly.

A few rules make the table work.

  • Reviews never go cheap. A weak reviewer passes weak work. If anything, the reviewer should be at least as strong as the builder.
  • Review across families. A model from a different provider than the builder catches different mistakes. Two models with the same blind spot agree with each other.
  • Escalate on failure. If a job fails at one tier, try the next one up, rather than rewording the prompt five times.
  • Never let the builder grade its own work. Keep planning, building and judging separate, even if the same model does all three in different sessions.

Model and effort are separate dials

Most tools let you set how hard a model thinks, as well as which model it is. These are different controls. A strong model on low effort is often better than a weak one on maximum effort, and maximum thinking by default wastes time and money on easy jobs. Turn effort up for the hard step, not for the whole session.

Set it in the control, then check

Writing "use the strongest model for this" in a prompt does nothing. The model cannot change which model it is. Set the model in the tool's settings or in the configuration for that job, then check what actually ran. Most tools show it in the status line or the logs.

Pick the model at the start of a session. Switching halfway through sends the whole conversation to a model with an empty cache, which is slow and expensive. If you need a different model, start a new session and give it a short handover file.

Subscriptions and quotas

Many people use agents on a subscription rather than paying per call. That changes the cost question. You are not paying per token, but you are spending a limited allowance over a time window. Burning a flagship model's quota on lookups means it is not there when you need it for a hard review. The tiers still apply, for a different reason.

Make your own table

Write down the jobs you actually give agents: "summarise a PR", "write unit tests", "plan a feature", "review a security change". Next to each, put the cheapest tier that does it well enough, and the tier you use to review it. Revisit it when a new model comes out. It takes ten minutes and saves a lot of guessing.
