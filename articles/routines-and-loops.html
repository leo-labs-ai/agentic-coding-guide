Routines, loops and guardrails

Once agents can work without you watching, the question changes from "how do I steer it?" to "how do I know it is still doing the right thing?"

About 4 minutes to read

Most agent work starts with a person typing a request. It does not have to. A lot of useful work is repetitive and predictable: checking dependencies, writing the weekly report, sweeping out stale docs, triaging new issues. Agents can do these on their own, if you build in the right guardrails.

Three kinds of routine

  • On a clock. Every night at two, every Monday morning. A scheduled job that starts an agent with a fixed brief.
  • On an event. A new issue is opened, a file lands in a folder, a build fails. The event starts the run and supplies the details.
  • In a session. While you work, an agent re-runs a check every few minutes, such as watching a deploy or a long test run, and tells you when something changes.

What every routine needs

A routine that runs unattended needs four things, and it is worth refusing to switch one on without them:

  1. Logs. What it did, when, and what it saw. If you cannot see a run, you cannot trust it.
  2. A "run now" button. So you can test it, and re-run it after a fix, without waiting for the schedule.
  3. A kill switch. One obvious way to stop it, fast.
  4. A health check. Something that notices when the routine has stopped running, or keeps failing. Silence should not look like success.

Add a fifth for the long term: a retirement condition. Routines accumulate. Write down what problem each one prevents and when it can be switched off.

Cheap checks, expensive thinking

Many routines spend most of their time finding nothing. Running a strong model every hour to discover that nothing has changed is waste. A better pattern is a heartbeat: a cheap check, often plain code, that looks for change and wakes the expensive model only when there is something to think about.

At Fernhill Supply, a script checks the supplier price list every morning. Most days it is unchanged and the script exits. When it changes, an agent compares the new prices against the shop's margins and drafts a list of products to review. A person approves any price change.

Three kinds of loop

A routine runs on a schedule. A loop runs until something is true. There are three useful kinds.

Run until a stop condition

The simplest: "keep going until the test suite passes", or "work through every file in this folder". Good for long, mechanical jobs you would otherwise babysit, such as a big migration run overnight. The stop condition must be checkable by a machine. "Until it looks good" is not a stop condition.

Measure and improve

Sometimes called hill-climbing or an eval loop. You define what good looks like, measure the current version, make a change, and measure again. Keep the change if the score improves. This is how you improve a prompt, a skill or a routing rule with evidence rather than feel.

The rule here is firm: do not optimise a skill without a benchmark. Without one, you are just automating vibes. A benchmark does not need to be fancy. Ten cases is enough to start, with at least three taken from real failures, each with an assertion you can check, kept in a test tool or even a spreadsheet.

Supervision

For bigger jobs, one agent supervises several workers. Each worker gets a written brief, a status file it keeps up to date, and an inbox for questions. The supervisor reads the status files, answers what it can, and passes the rest to a person. The files mean nobody has to hold the whole picture in one context window.

Guardrails

Unattended agents fail in predictable ways. These rules catch most of them.

  • The worker never grades its own work. A separate checker, ideally a different model in a fresh session, judges the result against the criteria.
  • Every step cites evidence. "Fixed" is not a status. "Fixed: test checkout_retry now passes, log attached" is.
  • Two strikes, then stop. After two failed attempts to fix the same thing, the loop stops and asks for the task to be re-scoped. A third attempt in the same direction rarely works, and it burns budget.
  • Done is not accepted. A loop meeting its stop condition means the machine-checkable part is finished. A person still decides whether the work is good.
  • Some actions always need a yes. Sending, deleting, paying and publishing wait for a human, however long the loop has been running smoothly.
  • Budgets are hard limits. Each run has a ceiling on time and spend. Hitting it stops the run and reports where it got to.

Improving the harness itself

The most valuable loop is the one that improves the harness. When an agent keeps failing at a kind of job, work through it in order:

  1. Run the current setup on a fixed set of cases to get a baseline.
  2. Find the earliest point in a failed run where things went wrong, the first bad handoff, not the final error.
  3. Make the smallest change that would have prevented it: a line of instruction, a check, a step in a skill.
  4. Rerun from fresh on the same cases, plus a couple you held back.
  5. Keep it, revise it, or remove it, based on the result.

One easy step to skip: confirm the change was actually used. A new skill that never loaded, or an instruction that was cut off, will appear to "not help" for the wrong reason.

Keep a scar list

When an agent makes the same mistake twice, write it down, along with the fix you put in the harness. Over time this list becomes the best guide you have to what your setup needs. It also stops you fixing the same output by hand every week. Fix the harness, not the output.
