The agent loop and acceptance criteria

An agent is only as good as its idea of "done". A worked example, from a bug report to a fix someone can approve.

About 5 minutes to read

Fernhill Supply sells garden tools online. Customers have started getting charged twice. The support team traced it to the checkout page: if someone double-clicks Pay, or the network is slow and they click again, two orders go through.

Sam, the developer, hands the bug to a coding agent. This article follows what happens, and where it can go wrong.

The loop

Under the hood, every agent does the same thing. The model reads its context and either answers or asks for a tool: read this file, run this command, open this page. The harness runs the tool and adds the result to the context. The model reads again and decides the next step. Round and round, until it decides it is done or something stops it.

Good runs give that loop a shape:

  1. Orient. Read the bug report, the checkout handler, the orders API and any notes in the repo about payments.
  2. Plan. Say what it will change and how it will know the change worked.
  3. Execute. Make the change on a branch.
  4. Judge. Run the checks against the criteria. If they fail, go back to the plan.
  5. Learn. Record what happened so the next run starts smarter.

The loop is bounded by three things: the tools the agent may use, the budget it has, and the permissions it holds. Inside those bounds, the only thing that decides when it stops is its idea of done. That is why acceptance criteria matter more than anything else in the brief.

The tempting fix

Ask an agent to "fix the duplicate orders on double-click" and there is a good chance it does this: find the Pay button, disable it after the first click, run the page, see that a second click does nothing, report success.

It looks right. It even passes a quick manual test. But it does not fix the bug. A slow network can still send the request twice. A customer can refresh mid-payment. A mobile browser can retry on its own. The button was only ever one way in. The real problem is that the server creates a new order every time it receives the request.

The agent did nothing wrong by its own lights. It was asked to stop duplicates on double-click, and it did. The brief described a symptom, so the agent fixed the symptom.

Writing the criterion

A good acceptance criterion describes the outcome the business cares about, in a form a check can prove. For this bug:

One intended purchase produces exactly one order, including when the same request arrives more than once.

That sentence changes the work. A disabled button cannot satisfy it on its own, because it says nothing about repeated requests. The agent now has to look at the server: an idempotency key sent with the payment request, say, so the API recognises a repeat and returns the existing order instead of creating a new one.

It also tells the agent what proof to collect. Two checks, not one:

  • A browser check. Open the checkout, double-click Pay, and confirm one order exists.
  • An API check. Send the same payment request twice with the same key, and confirm the second call returns the first order rather than a new one.

The patch plus both results is something Sam can actually review. Without the API check, Sam would have to reason about every retry path personally, which is exactly the work the agent was meant to save.

What good proof looks like

When the agent finishes, Sam should get a short handover, not a story:

Change: idempotency key on POST /orders; Pay button disabled while pending.

Criterion: one intended purchase creates one order,
including repeated requests.

  Browser: double-click Pay           1 order created   PASS
  API: same request sent twice        1 order created   PASS
  Existing checkout tests             all passing       PASS

Not changed: refunds, order emails.

Each line is checkable. Sam can open the diff, rerun either test, and decide. The agent saying "I fixed it and tested it" is a claim. This is evidence.

When it still stops short

Suppose Sam writes the criterion well and the agent still stops after disabling the button. It reports the browser check, skips the API check, and calls it done.

Correcting it in the chat would work for today. A better move is to ask what in the harness let it stop there. Perhaps the debugging skill the agent loaded says "reproduce the bug, fix it, confirm the reproduction no longer fails", and never mentions retries. The agent followed its procedure exactly.

So Sam adds one step to the debugging skill: "For anything that creates, charges or sends, also check that a repeated request has no extra effect." That is a small change that will apply to every future bug of this kind, not just this one.

Then Sam checks that the change actually helps. Run the original setup and the changed one on the same set of cases: this bug, a couple of similar ones from the history, and one or two held back that were not used while writing the new step. If the new version catches the retry case and does not make anything else worse, keep it. If not, revise or remove it. A change to a skill that has not been measured is a guess.

Outside of code

The same shape works for office work. Take a weekly project report. Code filters the project list down to the overdue items, so the model never has to read the whole spreadsheet. A reporting skill supplies the format. The model writes the explanations and flags any project with a missing status rather than guessing one.

The criterion might be: every overdue project appears once, with its owner and the reason it is late, and any project without a status is listed separately. A person can check that in two minutes.

The habit

Before you hand a job to an agent, write one sentence that says what must be true when it is done, and how you would check it. If you cannot write that sentence, the agent cannot either, and it will pick its own idea of done. It will usually pick the easiest one.
