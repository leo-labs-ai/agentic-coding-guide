Prompt caching and the recurring cost of a prompt

Every line you add to an agent's standing context is paid for again on every turn. Caching softens that. It does not remove it.

About 5 minutes to read

This article is about concepts, not prices. Rates differ between providers and change often. The shapes below do not.

Every turn starts from scratch

Models do not remember between calls. When an agent takes its tenth step in a session, the harness sends the model everything again: the system prompt, the tool definitions, your instructions, the skill descriptions, and all nine earlier steps with their tool results. The model reads the lot, then produces the next step.

So a session costs far more than what you typed. You pay to re-read the whole context, once per turn.

What caching does

Providers soften this with prompt caching. If a request starts with exactly the same text as a recent one, the provider can reuse the work it already did on that opening stretch, the prefix, instead of processing it again. Cached reads are cheaper and faster than fresh ones.

Harnesses arrange requests to take advantage of this. The things that never change go first: tool definitions, then standing instructions. The things that change go last: new messages and tool results. Each new turn shares a long prefix with the one before.

Two points are easy to miss.

  • Cached tokens still fill the window. Caching changes the price of reading the prefix, not its size. A bloated AGENTS.md crowds the model's attention whether it is cached or not.
  • Cached tokens are still paid for. They are billed on every read, at a lower rate. Cheaper is not free.

How the cost grows

It helps to picture three shapes.

A fixed prefix grows linearly. Standing instructions are re-read on every turn. At a fixed rate, a prefix five times larger costs five times as much, on every turn, for the life of every session. Trimming a long instructions file is one of the few changes that pays off on every single call.

A growing history grows faster. Each turn adds to the conversation, and each later turn re-reads everything before it. Turn one reads one step, turn two reads two, turn three reads three. Add those up across a long session and the total climbs much faster than the session length. This is the maths behind "new task, new session". A fresh session resets the sum.

Delegation can multiply. When an agent hands work to sub-agents, and they hand work to their own sub-agents, each layer carries its own context. Done carelessly, the cost multiplies with depth. Done well, it is a saving: each sub-agent gets a small, focused context instead of inheriting the parent's whole history, and hands back a short result.

What breaks the cache

The cache only matches an identical prefix. Change anything early in the request and everything after that point has to be processed fresh.

  • Live values in standing instructions. A date, a counter or a status line near the top of the prompt changes every session, or every turn, and invalidates everything below it. Keep instructions static. Put live facts in a message at the end, or in a file the agent reads when it needs to.
  • Editing early memory. If a memory block near the start is rewritten, the cache breaks from that point. Appending at the end keeps the prefix intact.
  • Switching models. Caches belong to one model. Switch mid-session and the whole conversation is sent to a model with an empty cache. Pick the model at the start.
  • Reshuffling tools. Adding, removing or reordering tool definitions changes the very start of the prefix.

A related trap: a memory file on disk does nothing by itself. It only affects behaviour once the harness injects it into the context, and where it is injected decides what it does to the cache.

The counterintuitive result

Because cached reads are so much cheaper than fresh ones, a larger model running on a warm cache can cost less per turn than a smaller model that keeps busting its cache. "Use the small model to save money" is often right for one-off jobs. In a long session, cache behaviour can matter more than the headline rate.

The same thinking explains why a gateway that reports cache hit rates is worth having. A sudden drop usually means someone put a timestamp in a prompt.

Filtering before the model

The cheapest token is one the model never reads. If an agent needs ten rows from a large export, a few lines of code that filter the export first beat pasting it in. Some harnesses lean into this: the model writes a short script, the script does the heavy lifting, and only the result comes back into the context. This is sometimes called code mode, and it keeps both cost and context in check.

A worked comparison

Sam's team at Fernhill Supply has two setups for the same repo.

In the first, AGENTS.md has grown to several hundred lines, including a "current sprint" section with today's date at the top. Sessions run all day, and people switch models when they get stuck.

In the second, AGENTS.md is twenty lines of rules and pointers. The sprint notes live in a file the agent reads when asked. Each task gets a fresh session, and the model is chosen at the start.

The second setup re-reads a fraction of the prefix on every turn, keeps its cache warm because the prefix never changes, resets the growing history with each new task, and never sends a full conversation to a cold model. Nobody had to negotiate a better rate. They just stopped paying for the same text over and over.

Rules of thumb

  • Keep standing instructions short and static.
  • Put changing facts at the end, or in files read on demand.
  • Start a new session for a new task.
  • Choose the model at the start, and leave it.
  • Give sub-agents small contexts and ask for short results.
  • Filter big data with code before the model sees it.
